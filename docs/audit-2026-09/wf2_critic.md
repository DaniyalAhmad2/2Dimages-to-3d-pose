## PLAN RISKS
The deepest risk is that the audit answered a well-posed question that may not be the client's question. Every headline number is positional, computed against the take's own measurement, in the live-view coordinate frame: retarget error cannot see error already in its input (baseline caveat 4), epipolar error cancels a focal that is wrong the same way in both cameras (caveat 2), the tag holdout uses the assumed marker size as its own ground truth, and the whole error budget stops at Character.pose_bone_matrices. A plan that optimises those numbers can ship an animation that looks worse: the audit's own PIL renders say the visibly wrong parts are the feet and hands (angular errors invisible to every positional metric), and the client's actual deliverable — a 772-frame BVH of which 26 poses are real — was never opened. Rank by what is visible in the file the client watched, not by millimetres. Second, one take, 26 frames, one rig, zero corrections: per-joint medians rest on 25 samples, every 'max' is a single frame, the live-edit findings come from a Qt-free reimplementation rather than the real widget, and the take is not representative of its own successor — only 11 of its 26 frames have any tag common to both cameras, tag 13 returns the wrong IPPE branch in 35 % of solves and is only harmless because the right camera never sees it, and nothing in the app detects a camera that moved. 'Not the cause' verdicts on extrinsics and intrinsics are verdicts about this scene's shape error, not certificates that the calibration is right; the same code is one framing change away from a 94 %-dropout failure with no diagnostic. Third, the fixes are not independent, and the audit measured them one at a time: Halpe-26 changes the NECK/PELVIS definitions that the bone-length targets, the symmetric-target proposal, the uniform scale and the retarget root all consume; F16's restored face keypoints meet a head path that still assumes HEAD is the nose; the roll fix changes exactly the quaternions the exporter keyframes and interpolates; F09's preserved NaNs reach a retarget whose gap behaviour has only been tested for exceptions; F13's root motion changes the view's auto-framing rule. A combined build must be re-measured as a build, with the ship gates fixed in advance, or the regressions will cancel the wins invisibly. Fourth, the delivery mechanics can nullify the whole effort: opening an existing project never recomputes, so the client can install the fixed build, open Imported_Session, and see exactly what they complained about; the moment they press Recalibrate the pose moves by up to 22 % of body height with no version stamp explaining why; and the only route to head keypoints on an old project is the button that erases their manual corrections. Finally, absolute scale is unresolved and possibly irrelevant in a way nobody has checked — if fit_to_subject normalises it away, the client cannot export a true-size figure no matter which number the spinbox holds, and if the printed tag is not 50 mm every millimetre figure in the audit is off by that factor while every shape conclusion stands. One ruler measurement from the client, and one confirmation of which file they were judging, would de-risk more of this plan than any further internal experiment.
